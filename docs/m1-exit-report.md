## Issues found

1. **Trade failure paths are not reached by the documented 30-minute economy command.** With the defaults (`Economy.TradeScope=Allied`,
   `TradeRequiresProximity=true`, hostile `--relations ffa` teams) clients propose 1,344 trades and none is accepted, so
   `--trade-fail 10 --trade-timeout 5` and the InDoubt resolution are not exercised (rejects: ScopeDenied, RateLimited, OutOfRange).
   The run still verifies idempotency, the auditor and reconciliation. Suggestion: document in `fakenode.md` the server settings a trade run needs
   (`Teams.AllowAssetTransfer=true`, `Economy.TradeScope=Anyone`, `Economy.TradeRequiresProximity=false`), or let `--relations`
   print them; row 5b shows that with them the failure/timeout path works (124 completed, 25 rolled back, 4 withheld, 0 in doubt at the end).
2. **One `POST /api/v1/sessions` with a `saveId` of a just-uploaded save answered 404 once**, directly after the upload `complete`. The same call a
   minute later (and with the same sha) returned 201. Not reproduced; hypothesis: the save catalog entry was not yet visible to the session
   endpoint right after `complete` (a race), or the first call hit a session that had just been stopped. Worth a test.
3. **Login throttling is easy to hit when scripting.** Five quick logins gave 429 (`Retry-After: 6`, audited as `auth.login.throttled`). Working as
   designed; for scripts use `POST /api/v1/tokens` (Bearer) after one login.
4. **`--X4MP:Net:...` command-line keys work for ports and limits** (used throughout instead of env vars); `fakenode.md` and `server-admin.md` only mention the env form.
5. **Not measured wire-side:** the "relation change reaches every node within 1 s" bound is asserted by the Playwright teams spec, not timed by a
   separate probe; the 30-minute runs did not change relations mid-run (`relation-changes=0`). The criterion 1 GUI items (9 nodes with ping/FPS/bandwidth)
   were not eyeballed in a browser; the map and players specs cover live positions and the player list.
6. **Harness output through a pipe can look like a failure.** `dotnet run ... | Select-Object -Last N` returned exit 255 once while the harness
   run kept going in the background (orphaned server and swarm); the run is reliable when started as its own background command.

Everything started for these checks was stopped afterwards; data dirs stay under `out/m1exit/` (git-ignored).
